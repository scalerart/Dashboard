# Render + MongoDB Atlas deployment runbook

The repository is configured as one Render Web Service: Express serves both the Vite-built React app and `/api/*` from the same origin. This keeps the secure session cookie same-site and requires no separate static-site service. The root `render.yaml` defines the service, health check, build/start commands, and environment-variable prompts.

The deployment is not complete until the provider settings and launch checks below pass. Never commit secrets or paste them into chat. Rotate any password that has been shared.

## 1. Prepare MongoDB Atlas

1. Create a dedicated Atlas database for this app on a replica-set cluster that supports transactions. Invoice, payment, and purchase workflows use MongoDB transactions.
2. Create a database user with a strong unique password and read/write access only to this app database. Startup creates the required collections and indexes.
3. In the Render service's **Connect → Outbound** panel, find its outbound IP ranges. Add the ranges for the service's region to Atlas Network Access. Render's shared ranges are shared with other services in that region; dedicated outbound IPs are a paid Render workspace feature. Do not use `0.0.0.0/0` as a production shortcut.
4. Copy the Atlas URI, including the dedicated database name, into Render as `MONGODB_URI`. Keep it out of the repository and local `.env` files.
5. Enable Atlas backups and set suitable retention. Test restoring a snapshot into a separate temporary cluster. Atlas backup recovery is separate from the application's owner ZIP export.

## 2. Create the Render service from GitHub

1. Push the deployment-ready commit to `https://github.com/scalerart/Dashboard`.
2. In Render, choose **New → Blueprint** and connect the `scalerart/Dashboard` repository. Render detects the root `render.yaml`; keep the root directory as `.`.
3. Review the Blueprint service named `maa-offset-press`. Choose a paid service plan for an always-on production business app; free instances may sleep and have limited resources.
4. Supply the prompted secret values privately in Render. The Blueprint generates a `JWT_SECRET`; keep it private and do not rotate it casually, since doing so invalidates existing sessions.
5. Apply the Blueprint and wait for the build and deploy to finish. The service uses:
   - Build: `npm ci --include=dev && npm run build`
   - Start: `npm run start --workspace @maa/api`
   - Health check: `/api/health`
   - Node.js: the Node 22 range specified by the root `package.json`.
6. Wait for the service to become **Live**, then open its `https://<service>.onrender.com` URL. The React app and API are on that same URL.

## 3. Configure environment variables

The Blueprint includes the required keys. Check them in Render under **Environment** and add/update these values:

| Variable | Value / handling |
| --- | --- |
| `NODE_ENV` | `production` |
| `MONGODB_URI` | Atlas URI for this app's dedicated database |
| `JWT_SECRET` | Generated by Render; at least 32 characters |
| `CLIENT_ORIGIN` | Leave unset for the generated Render domain; the app derives it from Render's `RENDER_EXTERNAL_URL`. For a custom domain, set the exact `https://` origin and redeploy. |
| `TRUST_PROXY_HOPS` | `1` |
| `CURRENCY`, `VITE_CURRENCY` | Same three-letter currency, `BDT` by default |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | Real SMTP provider settings; required for email verification and invoice email. `SMTP_PORT` defaults to `587`. |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | Optional; required only if document storage is to be enabled. |
| `DEV_EMAIL_VERIFICATION_LINKS` | Must remain `false` |
| `ALLOW_REMOTE_DEVELOPMENT_DATABASE` | Must remain `false` |

Use the Render dashboard's secret fields for credentials. Do not put database, JWT, SMTP, or Cloudinary secrets in `VITE_*` variables. If a custom domain is added, set `CLIENT_ORIGIN` to that exact origin; otherwise verification emails keep pointing at the Render hostname.

## 4. Database initialization and existing installations

- For a brand-new empty Atlas database, the first API startup checks for unmigrated tenant records and creates the required indexes. `/api/health` becomes healthy only after the database is connected and startup initialization succeeds.
- If this database already contains legacy app data, do not deploy against it before migration. Stop writes, take and verify an Atlas snapshot, then run `npm run build --workspace @maa/api` and `npm run migrate:tenants --workspace @maa/api` once from a trusted environment with the intended `MONGODB_URI` and `JWT_SECRET`. This command mutates legacy records and synchronizes indexes.
- Startup fails closed if tenantless records or unmigrated counters are found. Check Render logs for the migration error; do not bypass it or point the migration command at an unverified database.

## 5. Verify the live deployment

Before entering real business data:

1. Confirm `/api/health` returns HTTP 200 with `"status":"ok"` and `"database":"connected"`. Check Render deploy and runtime logs for startup errors.
2. Create a test owner account and confirm the verification email arrives at the configured test inbox. Verify, sign in, sign out, and test password/session behavior.
3. Register a second test business and confirm it cannot see or change the first business's customers, invoices, inventory, alerts, reports, or backup.
4. Exercise create/list/edit/archive/search/pagination for customers and the relevant order, invoice, payment, expense, income, inventory, supplier, purchase, and account workflows.
5. Verify invoice PDF/email, payment idempotency, due calculations, purchase stock/cost updates, reports/CSV, document upload/download (if Cloudinary is enabled), notification actions, and owner-only ZIP export.
6. Test mobile, tablet, and desktop layouts. Review Atlas access/backup configuration, Render logs, SMTP deliverability, and service billing.
7. Use a disposable replica-set database for `npm run test:integration`. It must not be production: the suite creates and drops a uniquely named `maa_offset_test_*` database.

Do not treat deployment success or a healthy endpoint as proof of all accounting workflows. Reconcile test results and verified opening records with the business before using live financial data.

## Runtime limitations and unimplemented workflows

- Document uploads and workspace ZIP exports are capped at 4 MB. Larger direct-to-Cloudinary uploads/object-storage backup and tenant ZIP restore are not implemented.
- SMTP is required for public signup and invoice email. Cloudinary is optional.
- Atlas backups provide database recovery; scheduled application backups and scheduled reports are not implemented.
- Opening balances, transfers/account reconciliation, cost-of-sales, and validated profit reporting are not implemented. Account totals represent recorded net movement, not verified available cash.
- A complete replica-set integration run, real SMTP/Cloudinary checks, restore drill, and authenticated browser test must be done with the provider credentials and test resources; these cannot be certified by a build alone.

## Accounting cutover

No verified business workbook or opening balances were available. Do not invent cash, bank, inventory, customer-due, supplier-due, tax, or profit values. Choose and document a cutover date; reconcile physical inventory and receivables/payables against source documents with the business's accountant before relying on financial reports.
